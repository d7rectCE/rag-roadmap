# Async HTTP Fetcher

Учебный проект: модуль 0 роадмапа по RAG/NLP.

Асинхронный HTTP-клиент, который параллельно опрашивает список URL, переживает
сетевые сбои и уважает ограничения на стороне сервера. Написан, чтобы разобраться
с `asyncio`, ретраями и rate limiting на реальной сети, а не на заглушках из
`asyncio.sleep`.

## Что делает

- Параллельно опрашивает произвольный список URL
- Ретраит временные ошибки (429, 5xx, таймауты) с экспоненциальным backoff и джиттером
- При 429 слушается заголовка `Retry-After` вместо того, чтобы гадать по формуле
- Не ретраит постоянные ошибки (404, 400, 401) — повтор даст тот же ответ
- Держит два независимых ограничителя: по скорости и по параллельности
- Пишет структурированный JSON-лог по каждой попытке
- Возвращает валидированные pydantic-модели и сводную статистику по прогону

## Запуск

```bash
uv sync
cp .env.example .env
uv run python -m fetcher
```

Тесты:

```bash
uv run pytest
```

Настройки в `.env`:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `TIMEOUT_SECONDS` | 3.0 | Таймаут чтения ответа |
| `MAX_RETRIES` | 3 | Число повторов (всего попыток на одну больше) |
| `MAX_CONCURRENT` | 5 | Максимум одновременных запросов |
| `RATE_LIMIT_PER_SECOND` | 2.0 | Максимум запросов в секунду |
| `LOG_LEVEL` | INFO | Уровень логирования |

## Два ограничителя

Главная вещь, которую этот проект должен был показать: **скорость и параллельность —
разные оси, и один ограничитель не заменяет другой.**

| | `Semaphore` | `TokenBucket` |
|---|---|---|
| Что ограничивает | Сколько запросов летит одновременно | Сколько запросов в секунду |
| Кого защищает | Клиента: сокеты, память | Сервер: его лимит |
| Если убрать | Тысячи открытых соединений | 429 и бан |

Почему их путают: `Semaphore(5)` при запросах по 100 мс даёт 50 запросов в секунду —
3000 в минуту. Если API разрешает 60 в минуту, лимит пробивается в 50 раз, при том
что семафор формально «стоит». Он и не должен был это ловить — он про другое.

Проверить можно на самом проекте: поставить `MAX_CONCURRENT=10` и
`RATE_LIMIT_PER_SECOND=1` — запросы всё равно пойдут по одному в секунду.

## Обработка ошибок

| Класс | Коды | Поведение |
|---|---|---|
| Успех | 2xx, 3xx | `status="ok"` |
| Временная | 429, 500, 502, 503, 504 | Ретрай с backoff, при 429 — по `Retry-After` |
| Постоянная | 400, 401, 403, 404 | Ошибка сразу, без ретрая |
| Сетевая | таймаут, `ConnectError` | Ретрай с backoff |

Провал одного URL не считается исключительной ситуацией: он превращается в
`FetchResult(status="error")` и не мешает остальным запросам. Поэтому основной
режим — `asyncio.gather`, а не `TaskGroup`.

Статистика в конце прогона показывает `total_attempts` рядом с `total` — разница
между ними и есть цена ретраев.

## Чему научился

**Семафор — не rate limit.** Ограничение параллельности и ограничение частоты
измеряют разные вещи. Пять одновременных запросов по 100 мс — это 3000 запросов
в минуту, что пробивает лимит в 60/мин, хотя семафор при этом работает штатно.
Нужны оба ограничителя.

**Сервер сам говорит, сколько ждать.** При 429 в ответе почти всегда есть заголовок
`Retry-After` с точным временем. Экспоненциальный backoff — это догадка, которая
может снова попасть в то же окно лимита. Правильный порядок: сначала читать
заголовок, формула только как запасной вариант.

**Ретраить нужно не всё.** 404 не станет 200 от четвёртой попытки. Разделение
ошибок на временные и постоянные экономит время, запросы и деньги — и это видно
в логе по полю `attempts`.

**Ресурс не держат, пока ждут.** Если уснуть внутри `async with semaphore`, слот
будет занят корутиной, которая ничего не делает. При `Retry-After: 60` это
блокирует слот на минуту. Пауза должна быть снаружи блока, удерживающего ресурс.

**`async` сам по себе не ускоряет.** Ускоряет одновременный запуск задач —
`asyncio.gather`. Последовательные `await` работают ровно столько же, сколько
синхронный код.
